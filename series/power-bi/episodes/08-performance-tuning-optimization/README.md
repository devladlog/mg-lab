# DEVLADLOG Power BI #8: Performance Tuning & Optimization

Same **Contoso Bikes** project as episodes 1-7. The order-line export has grown to two million lines and the executive
page is slow. Instead of guessing, this episode **measures first**, then changes one thing at a time and checks that the
numbers on the report don't move:

1. a deterministic generator makes the fictional export (`gen_sales.py`: text order numbers with a prefix, timestamps to
   the second, a per-line reference, a free-text note: the usual suspects)
2. two semantic models built from one description: **Before** (everything the guidance warns about) and **After** (same
   tables, same measure names, same answers)
3. two PBIR reports: Before has one 13-visual page including a table of every order line; After has 7 visuals and the order
   lines on their own page
4. `perf-lint` finds the guidance violations in the TMDL and PBIR files, `reduce-demo` measures what the data reduction does
   to every column, `perf-compare` puts the Performance Analyzer numbers of both reports side by side
5. DAX queries for DAX query view: real column sizes and the before/after measure comparisons (**need Desktop**)

## What changed between the two models

| Area | Before | After | Rule |
|---|---|---|---|
| Hidden date table per date column | `LocalDateTable_OrderDate` (stand-in for what Auto date/time adds) | none, one `Date` table | PF001 |
| Product relationship | `bothDirections` | single direction | PF002 |
| Line amount | DAX calculated column | computed in Power Query | PF003 |
| `Order Timestamp` | datetime to the second in the model | dropped, `Order Date` kept | PF004 |
| `Line Ref` | 200,000 distinct values in 200,000 rows | dropped | PF005, PF011 |
| `Order Number` | text `SO-0000123` | whole number | PF006 |
| `Note` | hidden, unused | dropped | PF011 |
| Online Sales | `FILTER('Store', ...)` | `KEEPFILTERS('Store'[Channel] = "Online")` | PF007 |
| Margin % | `IFERROR([Margin] / [Sales Amount], 0)` | `DIVIDE([Margin], [Sales Amount])` | PF008 |
| Sales YoY % | the same `CALCULATE` twice | one `VAR`, used twice | PF009 |
| Executive page | 13 visuals incl. a table of every line | 7 visuals; order lines on their own page | PF010 |

`perf-lint` rules (each one is a Learn recommendation; the thresholds that aren't Learn's are marked):

| Rule | Severity | Finds |
|---|---|---|
| PF001 | warning | auto date/time table (calculated table named `LocalDateTable_*`/`DateTableTemplate_*` built with `CALENDAR`; the naming is how Desktop writes it, not documented on Learn) |
| PF002 | warning, info | bi-directional relationship; **info** when it is also a security filter (row-level security needs it: keep it) |
| PF003 | warning | calculated column in a table that Power Query loads |
| PF004 | warning | date/time column with a time part in a table that isn't the date table |
| PF005 | warning | column that is at least 50% distinct values (needs `--profile`; the 50% is our threshold) |
| PF006 | warning | text column that is always a prefix plus digits (needs `--profile`) |
| PF007 | warning | `FILTER(<table>, ...)` as a `CALCULATE` filter argument. Not flagged when the condition needs a measure, or `FILTER` runs over `VALUES(...)` (Learn: it's right there) |
| PF008 | warning | `IFERROR`/`ISERROR`, or `/` with a measure as denominator |
| PF009 | warning | the same `CALCULATE` twice in a measure without `VAR` |
| PF010 | warning | more visuals on a page than `--max-visuals` (default 10: **our** policy; Learn gives no number) |
| PF011 | warning | hidden column no measure, relationship, sort column, role or visual uses |

## Run it

```bash
# 1. data and reduction (standard library only)
cd src
python3 data/gen_sales.py --rows 200000 --out /tmp/export200k         # wrote 200,000 order lines + 4 dimensions ... (17.7 MB)
python3 tools/reduce_demo.py /tmp/export200k                          # 13 -> 9 columns, 136 -> 79 bits per row, totals identical
python3 tools/expected_totals.py /tmp/export200k                      # sales_amount 284798005.25, orders 80059 ...

# 2. models, reports, lint
python3 tools/build_models.py --check && python3 tools/build_report.py --check
python3 tools/perf_lint.py --model ContosoPerf.Before.SemanticModel/definition --report ContosoPerf.Before.Report \
    --profile expected/reduction-200k.json --profile-side before --brief       # 12 warning(s), 0 info
python3 tools/perf_lint.py --model ContosoPerf.After.SemanticModel/definition --report ContosoPerf.After.Report --strict   # 0 warning(s), exit 0

# 3. the M and the TMDL, checked by Microsoft's own libraries
cd pq-lint && npm ci --no-audit --no-fund && npm test && cd ..                          # tsc builds pq-lint
python3 tools/extract_m.py ContosoPerf.After.SemanticModel/definition /tmp/m && node pq-lint/dist/src/cli.js /tmp/m --strict   # 6 queries: 0 error(s)
dotnet build TmdlLoad -m:1 -v q && dotnet TmdlLoad/bin/Debug/net8.0/tmdl-load.dll ContosoPerf.Before.SemanticModel/definition
#   6 table(s), 1 parameter(s), 5 relationship(s), 0 role(s): loaded

# 4. tests (from the episode folder)
cd .. && python3 -m pytest tests -q                                  # 86 passed
```

| | |
|---|---|
| Columns in Sales | 13 -> 9 (`LineRef`, `Note`, `OrderTimestamp`, `UnitPrice` dropped; `OrderDate`, `LineAmount` added in both: the before model derives them too) |
| Distinct values | `OrderTimestamp` 80,006 -> `OrderDate` 1,096; `LineRef` 200,000 -> gone; `Note` 24,135 -> gone (200,000-line export) |
| Bits per row (sum of `ceil(log2(distinct))`) | 136 -> 79 |
| Totals | Sales amount **284,798,005.25**, Orders 80,059, Units 599,354 at 200,000 lines; **2,846,324,198.90**, 799,651, 5,999,533 at 2,000,000. Identical before and after, also for every month x store group (test) |
| What this does **not** tell you | the size in MB, or any time. Bits per value is the idea behind dictionary encoding, not VertiPaq's number; `OrderNumber` as a whole number shows no gain in this count (same distinct values), its gain (value instead of hash encoding) isn't visible here. ## What we learned / gotchas

- **Measure first.** Learn: Performance Analyzer records how long each visual takes, split into categories such as the time
  the DAX query took, and the visual's DAX query can be copied or run in DAX query view. The durations include time spent
  queued behind other operations on the UI thread, and the Desktop machine differs from the service (data volume,
  concurrency, capacity, caching): compare runs recorded the same way, and treat Desktop numbers as a guide.
  We did **not** build a parser for the Performance Analyzer *export* file: its format is documented in a Word file in
  Microsoft's sample repository that wasn't reachable from the build container, so `perf-compare` takes the durations you
  type in.
- **Size is cardinality.** Learn: VertiPaq compresses ~10x, but you should still load as little as possible: remove
  unneeded columns and rows, group and summarize, optimize data types (text with a prefix -> whole number, set the column
  to *Do Not Summarize*), prefer Power Query custom columns over DAX calculated columns (the latter compress less
  efficiently and are built after load), disable auto date/time.
- **Date/time columns.** Learn (relationships): the engine only has DateTime; a Date/Time column keeps its time part, and the
  fix for relationships is to remove the time in Power Query. A column with a time to the second is also nearly unique.
- **Auto date/time** makes a hidden calculated table per eligible date column (Import, date or date/time, not the many side
  of a relationship): model size and refresh time grow. Keep it only for simple models.
- **Bi-directional filters** can hurt query performance. Learn lists three legitimate uses; for slicers "with data" use a
  visual filter `is not blank`, for dimension-to-dimension questions use `CROSSFILTER` inside one measure. **Don't remove
  a security filter blindly:** the Customer relationship in episode 5's model is bi-directional because RLS needs it, so
  perf-lint reports it as *info*.
- **`FILTER` as a filter argument.** Learn recommends Boolean expressions (column stores are built to filter columns), and
  `FILTER` only when the condition needs a measure or several columns. **The rewrite isn't always the same measure:** Learn
  says the `FILTER('Product', ...)` form *replaces* filters on the table, `KEEPFILTERS` keeps them. Online Sales
  per store row differs between our two versions (the grand total agrees). `queries/02-*.dax` shows it; the narration
  assumes the result: check it on the recording day.
- **`DIVIDE` vs `/`**: use `DIVIDE` when the denominator could be zero or blank (BLANK, better than an alternate value for a
  measure); keep `/` for a constant denominator. `IFERROR` is no replacement: it hides every error.
- **`VAR`**: an expression used twice is evaluated once; Learn's YoY example runs in about half the query time.
- **Visuals per page.** Learn: limit the visuals on a page to what is necessary, put tables behind a Top N filter, use
  drillthrough and tooltip pages for detail. We moved the order lines to their own page; we did **not** add a Top N filter
  because the PBIR filter JSON isn't verified here. Our limit of 10 is policy.
- **Not verified on this machine (needs Desktop):** the M never ran (parser, lint, Python mirror and TOM only); both
  `.pbip` projects have not been opened in Desktop; no timing, memory or refresh duration was measured; the DAX queries
  weren't run (`INFO.STORAGETABLECOLUMNS` needs write permission on the model and doesn't work over a live connection,
  Learn); whether Desktop adds its own `LocalDateTable_*` tables to the before project and how it records the Auto
  date/time option in TMDL is unknown (the table in the before model is a hand-made stand-in).
