# DEVLADLOG Power BI #5: Row-Level Security

Same fictional **Contoso Bikes** model as episodes 1–4 (star schema, the episode 2 measures, the episode 4 report).
This episode adds **dynamic row-level security** for store managers and makes it testable at three levels:

- **The model** (TMDL): a hidden, unrelated mapping table `Store Access` (user → store), built from
  `store_access.csv` plus a `UpnDomain` parameter, so the repo only holds aliases; a dynamic role
  **Store Managers** that filters the **Store** dimension with `USERPRINCIPALNAME()` and also filters the mapping
  table itself; a **Head Office** role with no filters; *Apply security filter in both directions* on the one
  relationship that needs it (Sales → Customer); three "security check" measures (`Who Am I`, `Visible Stores`,
  `Visible Customers`) and a **Store security** report page that shows them
- **`rls-lint`**, a .NET tool on the Tabular Object Model (TOM): 12 rules on the roles in a TMDL folder (read-only
  roles, no comma in names, filters that reference real columns, `USERPRINCIPALNAME()` not `USERNAME()`, no
  `TRUE()` fallback, hidden and self-filtered mapping tables, `USERELATIONSHIP` next to RLS, what each role's
  filters reach and what they don't, one security-bidirectional relationship per table, inactive relationships).
  It also writes a TMDL view script with everything the episode adds
- **The expected matrix**: a Python reference applies the same rules to the same generated data and writes what
  every lab user must see (`reference/expected/rls_matrix.csv`)
- **An in-service test** (`service/Test-RlsMatrix.ps1`): one DAX query per user through the *Execute Queries* REST
  API with `impersonatedUserName`, compared with the matrix; PASS/FAIL per user, exit code 1 on any failure

## The model

```
 Store Access (hidden, no relationships)        role Store Managers
 User Principal Name | StoreKey        <----    Store:        StoreKey IN { stores mapped to USERPRINCIPALNAME() }
                                                Store Access: User Principal Name = USERPRINCIPALNAME()
            Store 1 ──▶ * Sales * ◀──▶ 1 Customer       (security filter in both directions)
                            * ▲
                    Date ───┘ └─── Product              role Head Office: no filters (every row)
```

## Run it

```bash
# lint the roles (and regenerate the TMDL view script)
cd src
dotnet run --project RlsLint -- ContosoSales.SemanticModel/definition --sensitive Customer \
    --script ContosoSales.SemanticModel/TMDLScripts/add-rls.tmdl
#   12 rules: 10 PASS, WARNING RLS009 (USERELATIONSHIP), INFO RLS006 (Head Office)  ->  0 error(s), 1 warning(s), exit 0
dotnet run --project RlsLint -- ../tests/fixtures/leaky-model/definition --sensitive Product
#   5 error(s), 7 warning(s), exit 1

python3 reference/rls_reference.py             # prints and writes reference/expected/rls_matrix.csv
python3 tools/build_report.py --check          # report matches the spec
python3 tools/report_lint.py ContosoSales.Report --model ContosoSales.SemanticModel/definition   # 0 error(s), 0 warning(s)

# tests (from the episode folder)
cd ..
python3 -m pytest tests -q                                              # 42 passed
dotnet test tests/RlsLint.Tests -m:1                                    # Passed: 16, Failed: 0
pwsh -NoProfile -Command "Invoke-Pester ./tests/RlsMatrix.Tests.ps1"    # Tests Passed: 11, Failed: 0
```

In the video, `rls-lint` is short for `dotnet run --project src/RlsLint --` (the assembly is `rls-lint.dll`).

## What we learned / gotchas

- **RLS doesn't apply to workspace Admins, Members or Contributors** (Learn: "RLS only restricts data access for
  users with Viewer permissions"). A store manager added as Contributor sees every store. That's the reason the
  in-service test exists; the Pester suite has a case for it. Whether `impersonatedUserName` also reflects the
  impersonated user's workspace role isn't documented; demo.md has a fallback shot for the gotcha.
- **A filter on Store doesn't hide Customer.** Filters go from the one side to the many side, so Store reaches Sales
  but not Customer, and the customer slicer listed all 301 names. `rls-lint --sensitive Customer` flags it (RLS010);
  the documented fix is *Apply security filter in both directions* on that relationship (Learn warns about
  performance, and a table can have it on only one of its relationships: RLS011). It's the one bi-directional
  relationship in the model; episode 1's `star-lint` would call it out, and that's deliberate.
- **`USERELATIONSHIP` and RLS.** The DAX reference says it can't be used when RLS is defined on the table the
  measure is in; the RLS article says more broadly it "might cause unexpected errors". Our `Sales by Ship Date`
  uses it with RLS on Store (not on Sales or Date), so `rls-lint` reports a warning, not an error; demo.md checks the
  measure under the role. Not verified in the engine yet.
- **Relationships can't have `///` descriptions in TMDL** (TOM: "Property 'description' is unknown"). We hit it again
  writing the comment for the bi-directional relationship; the reason lives in this README instead.
- **Members can't be assigned in Desktop** (Learn); the role files have no `member` lines, a test keeps it that way.
  Desktop's *View as > Other user* accepts any UPN, so the unmapped user is a Desktop-only check.
- **`USERNAME()` returns `DOMAIN\user` in Desktop and the UPN in the service** (Learn), so a filter that works in the
  service can fail in Desktop's View as. `rls-lint` asks for `USERPRINCIPALNAME()` (RLS004).
- **Test as role and dynamic RLS:** Learn says Test as role "uses your own identity when evaluating dynamic RLS
  expressions" and also that "Now viewing as" can test a specific person. The *Signed in as* card on the Store
  security page shows which identity is really used; the PowerShell test (impersonation) and the gotcha shot (a real
  Viewer session) don't depend on it.
- **Execute Queries limits** (Learn): tenant setting *Dataset Execute Queries REST API*, Read + Build on the model,
  120 queries per minute per user, and no service principals for models with RLS, so the test runs as a signed-in user.
- **Not verified on this machine (needs Windows + Power BI Desktop + the lab tenant):** the PBIP has never been opened
  in Desktop; the roles, the mapping table and the relationship properties are parsed by TOM (the same library
  Desktop and the service use), and the report files validate against Microsoft's schemas, but only Desktop and the
  service prove the numbers. The expected matrix is computed by the Python reference, not by DAX.
