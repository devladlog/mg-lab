# DEVLADLOG Power BI #9: Deployment Pipelines & ALM

Same **Contoso Bikes** star as episodes 1-8. Until now there was one workspace. This episode puts the model in a
**deployment pipeline** (Development, Test, Production) and builds what the service doesn't give you: a scripted release and
a check that runs before anything is promoted.

Blog guide: <https://www.devladlog.com/articles/power-bi/2026-05-02-deployment-pipelines-complete-guide-2026/>

1. a model whose stage specific values are **Text parameters** (`ExportsFolder`, `StageName`) so that **parameter rules** can
   set them per stage. Development reads three monthly exports, Test and Production read all 24
2. the monthly exports in a **SharePoint library**: the lab has no on-premises gateway yet (episode 14), and a service refresh
   needs a source the service can reach. Episode 7's Dataflow Gen2 source is **not** reused, see "gotchas"
3. `PbiPipelines`, a PowerShell module over the Power BI pipelines REST API, and `Invoke-PipelineRelease.ps1`
   (compare, check, deploy, wait, refresh; `-WhatIf` sends nothing)
4. `alm_check.py`: rules on the TMDL and the stage file, a diff mode for incremental refresh tables (used in episode 10)
5. a pull request gate for GitHub Actions that reads files only (no sign-in, no secret)

## Rules

| Rule | Severity | Finds |
|---|---|---|
| AL001 | error | a parameter with a rule that isn't type Text |
| AL002 | error | a rule for a parameter the model doesn't have |
| AL003 | error | rules on the Development stage (Learn: they can't be created there) |
| AL004 | warning | a data source address typed into the M instead of a parameter |
| AL005 | error | a data source rule on a source that is already a parameter (Learn: not supported) |
| AL006 | warning | `PowerPlatform.Dataflows`: a Dataflow Gen2 (CI/CD) source isn't deployable by a pipeline |
| AL007 | info | a PBIR report: Learn contradicts itself about PBIR and pipelines, deploy one and look |
| AL008 | warning | DirectQuery partitions together with auto date/time tables |
| AL010-AL012 | error | in `diff old new`: an incremental refresh table renamed, a non calculated column renamed, the policy removed |
| PD001-PD005 | error, info | in the module: a report without its model, more than 300 items, no target workspace, an unpaired name clash, nothing to deploy |

## What we learned / gotchas

- **Pairing, not copying.** Learn: items are paired by type and name, and the pairing is kept as a link. A deployment copies
  metadata, **not** data, permissions, refresh schedule, credentials or role assignments. So a new Test model is empty until
  it is refreshed with its own credentials.
- **Rules.** Parameter rules need **Text** parameters. A data source rule isn't supported when the source is a parameter:
  choose one. Rules can't be created in the Development stage, and a rule is applied at the **next** deployment.
  `stages.json` and `alm_check rules` only document the values: we found no REST call to set rules in Learn's pipelines API
  list, so they are entered in the UI.
- **The episode 7 architecture doesn't deploy.** Learn: a semantic model that uses a Dataflow Gen2 (CI/CD) item as its data source
  can't be deployed by a pipeline. This episode therefore reads files from SharePoint. (AL006.)
- **Fabric capacity.** Only a workspace on a Fabric capacity can be assigned to a stage. Custom pipelines of 2-10 stages are created in the
  UI, not by the API. 300 items per deployment, in the UI and the API.
- **Service principals.** Learn: a service principal can't configure OAuth credentials, becomes the owner of the deployed
  models, and a refresh then can't complete. The scripts here assume a signed in user.
- **API details.** The status values are NotStarted, Executing, Succeeded, Failed in the Power BI API (the Fabric API says Running).
  The stage artifact lists use different name properties for different item types (`artifactName`, `artifactDisplayName`): the
  module reads both. The Fabric `deploy` API takes stage ids and a note of up to 1,024 characters and doesn't support dataflows.
- **Incremental refresh.** The policy is copied by a pipeline; renaming an incremental refresh table or its non calculated
  columns, or replacing it with a model without a policy, fails the deployment. `alm_check diff` flags that before the
  deployment. (Episode 10 builds the policy.)
- **PBIR.** Learn's limitations list says PBIR reports aren't supported, the PBIR article says it's GA and the default.
  We could not settle it in the container. AL007 is an info finding; the recording deploys the report and shows the result.

## Not verified

- The M has never run: only the parser, the lint, the Tabular Object Model and the Python mirror checked it.
- The `.pbip` project was never opened in Desktop, and nothing ran against a real SharePoint site.
- The REST calls were tested with mocks shaped like Learn's samples, not against the service.
- Whether a PBIR report deploys through a pipeline.
