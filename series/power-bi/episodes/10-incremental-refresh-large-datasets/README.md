# DEVLADLOG Power BI #10: Incremental Refresh & Large Datasets

Same **Contoso Bikes** star, now with a two million line order table in a database. Reloading all of it every night to pick up
ten days of changes is wasteful. This episode builds an **incremental refresh policy**, works out which partitions it creates,
and refreshes a single partition. Episode 9's checks and pipeline are not repeated: a pipeline copies the policy, and renaming
an incremental refresh table fails the deployment (`alm_check.py diff` in episode 9 catches it).

Blog guide: <https://www.devladlog.com/articles/power-bi/2026-04-01-incremental-refresh-complete-guide-2026/>

1. `sql/`: three T-SQL scripts for a **free-tier Azure SQL Database** (the lab has no gateway until episode 14, so a service
   refresh needs a cloud source): a deterministic 2,000,000 line table over 2023-2026, late corrections, checks
2. `sql_mirror.py`: the same arithmetic in Python, so the expected totals are known without a server
3. a model (TMDL) with `RangeStart` / `RangeEnd`, a filter on `OrderTimestamp`, and a `refreshPolicy` (keep 3 years, refresh 10
   days, detect data changes on `ModifiedDate`), plus a one page PBIR report
4. `ir_partitions.py`: which partitions a policy creates on a given day (Learn's rules, Learn's worked example is a test)
5. `ir_lint.py`: eleven rules (IR001-IR011) on the TMDL
6. `PbiRefresh`, a PowerShell module for the enhanced refresh API, and `Invoke-PartitionRefresh.ps1`

## What the partitions are

Learn (advanced incremental refresh): the refresh period is the last N periods up to and including today; older rows back to the start
of the store period sit in whole historical periods: years, then quarters, months, days. A quarter or year exists only when complete.
Day partitions merge into a month on the first of the next month, months into a quarter, quarters into a year. With real time
there is a DirectQuery partition after the refresh period. Learn's example (today 2021-02-02, 3 years, 1 day, real time) gives
2018, 2019, 2020, January, 1 February, today, DirectQuery. `ir_partitions.py` reproduces it. For the lab policy on 2026-11-21:

```
$ python3 tools/ir_partitions.py --model ContosoSalesIR.SemanticModel/definition --date 2026-11-21 --rows-from ../expected/daily-2m.json
  historical  2023           2023-01-01 .. 2024-01-01    499,655 lines
  historical  2024  ...  2025
  historical  2026Q1 / 2026Q2 / 2026Q3 (quarters), 2026Q410 (October), 11 day partitions for 1-11 November
  refresh     10 day partitions, 12-21 November
28 partition(s): 18 historical, 10 refresh
```

## Rules

| Rule | Severity | Finds |
|---|---|---|
| IR001 | error | `RangeStart` / `RangeEnd` missing or with another case (Learn: reserved, case-sensitive) |
| IR002 | error | a parameter that isn't type DateTime |
| IR003 | error | the filter isn't `>= RangeStart` and `< RangeEnd` (equals on both ends) |
| IR004 | error | a table with a policy whose partition doesn't use both parameters |
| IR005 | error | an invalid policy (refresh period not shorter than the store period, unknown granularity) |
| IR006 | warning | a source type without query folding (files, web) |
| IR007 | warning | a step before the date filter that usually stops folding (heuristic: confirm with View Native Query) |
| IR008 | error | the filter column isn't a `dateTime` column of the model |
| IR009 | error | detect data changes on the same column as the filter (Learn: it shouldn't be) |
| IR010 | warning | the detect-changes column isn't in the model (Learn: the design needs it persisted) |
| IR011 | warning | no polling expression: every refresh-period partition reloads every time |

## What we learned / gotchas

- **The parameters.** Reserved, case-sensitive, type DateTime. The filter uses `>=` on one side and `<` on the other, never equals on both:
  with equals a boundary row is loaded twice, with strict on both it is never loaded. It must fold; check View Native Query.
- **Don't publish twice.** Learn: after publishing you can't publish the same model from Desktop again (it removes the partitions and the data),
  and you can't download the file. Schema changes: ALM Toolkit or a metadata-only deployment (Premium / Fabric capacity, XMLA read-write).
- **Detect data changes.** The column shouldn't be the one used for the filter, and the design requires it to be persisted in memory:
  reduce its precision, or define the query through XMLA. Here `ModifiedDate` is a hidden column of the model.
- **Time.** The service decides the current day in UTC unless a time zone is configured under Refresh (XMLA refreshes default to UTC).
  *Only refresh complete days* is required with real time. We did not model it (it is not in `ir_partitions.py`).
- **Enhanced refresh.** `applyRefreshPolicy` defaults to true; with `commitMode = partialBatch` it must be false. `effectiveDate`
  overrides the day. A timeout of 5 hours per attempt by default, total including retries at most 24 hours; one refresh at a time
  (400 otherwise). History statuses: Completed, Failed, Unknown, Disabled, Cancelled. `add` isn't supported as a type.
- **Limits.** Scheduled refresh: 2 hours on Pro, 5 on Premium; XMLA refreshes have no time limit. Real time (hybrid) is Premium only.
  The portal doesn't show partitions: SSMS does, over the XMLA endpoint, which is read-only by default and must be switched to read-write by
  the capacity admin.
- **Pipelines.** A pipeline copies the policy; renaming an incremental refresh table or its non calculated columns fails the deployment (episode 9).
- **Free Azure SQL.** 100,000 vCore seconds, 32 GB, up to 10 free databases per subscription, `--use-free-limit true`, `AutoPause` or paid overage.
  It can't be restored or converted from an existing database. Open connections (SSMS, a pooled app) prevent auto-pause and spend the seconds.

## Not verified

- Nothing ran against a database, the service or Desktop: the SQL was only parsed (sqlglot, T-SQL), the M only by the parser, the
  Tabular Object Model and the lint; the policy TMDL syntax comes from a round trip through the Tabular Object Model, not from a file Desktop wrote.
- **Partition names.** Learn prints `2021Q101` (month) and `2021Q10201` (day). They fit both a calendar month number and a month-in-quarter
  number; `--month-style` has both, the default is the calendar month. The names of the refresh partitions and the DirectQuery partition aren't given.
- The calculator follows Learn's description and example, not the service's code. In particular, how a refresh period that crosses a
  month boundary is split is derived from the "whole period" rule, not from an example.
- The request id is read from the refresh history because `Invoke-PowerBIRestMethod` returns no headers here (Learn: it is the last segment of the
  `Location` header). Not tried against the service.
- `incrementalPeriodsOffset` appears in Learn's TOM sample; whether it equals *Only refresh complete days* is not confirmed, and the model leaves it out.
- Whether the service refresh can reach the Azure SQL server with only the server firewall settings described in demo.md.
