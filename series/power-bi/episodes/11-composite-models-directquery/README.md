# DEVLADLOG Power BI #11: Composite Models & DirectQuery

Same **Contoso Bikes** star as episodes 1-10. Until now every model imported its data. This episode keeps the large `Sales`
table in **DirectQuery** on SQL Server, makes the dimensions **Dual**, adds a hidden **Import aggregation** that answers the
common queries, and shows on the server which queries still arrive. Part B joins a local budget file to a published model,
which is the other thing a composite model is for.

Blog guide: <https://www.devladlog.com/articles/power-bi/2026-03-31-composite-models-complete-guide-2026/>

**No SQL Server and no Docker in the build container.** The SQL is generated for two dialects: T-SQL for the lab server
(CON-SQL01, SQL Server 2022, parsed by sqlglot here, never executed here) and SQLite, which the tests run to prove the data,
the aggregation view and the scale-up. Everything that needs SQL Server, Desktop or the tenant is marked "needs ..." below.

## Rules (composite-lint)

| Rule | Level | What |
|---|---|---|
| CM001 | warning | a limited relationship (many to many, or between different source groups); says why |
| CM002 | error | an `alternateOf` that can't work: detail table not DirectQuery, chained, type mismatch, Count on a non integer, duplicate |
| CM003 | warning | the aggregation table is not hidden |
| CM004 | error / warning | aggregation hits need regular relationships from the aggregation and from the detail table |
| CM005 | warning | a calculated column on a DirectQuery or Dual table that refers to another table |
| CM006 | info | with `--explain`: which measures and which dimension tables an aggregation can answer |

## What we learned / gotchas

- **Dual dimensions keep relationships regular.** Learn: relationships between tables of the same source (or Dual) are regular; an Import dimension next to a DirectQuery fact lives in another source group, so the relationship is limited and the aggregation can't be used through it. The linter flags it (CM001, CM004).
- **The aggregation must be hidden and mapped exactly.** Min, Max, Sum, Count and GroupBy; Count may use an integer column or "Count table rows" (`baseTable`); data types must match except for Count. Detail table in DirectQuery; no chains.
- **One measure can spoil it.** `Orders` is a `DISTINCTCOUNT` of the order number, which `Sales Agg` has no GroupBy column for, so it always goes to SQL Server. It is a miss on purpose, and so is `Customer` (not in the aggregation).
- **The aggregation grain is the point.** The scale-up grows the detail table to 2,035,500 lines and `vwSalesAgg` stays at 3,947 rows with the same totals (proved on SQLite).
- **Part B limits.** A model added next to a published semantic model is its own source group, relationships to it are limited; a chain of models is limited in length (Learn: three) and needs Build permission on each.
- **The linter predicts, the engine decides.** `--explain` applies Learn's rules, nothing is evaluated.

## Not verified

- The T-SQL has been parsed (sqlglot) but not run on SQL Server; the SQLite twin proves the logic only.
- No DAX has been run: no engine in the container. The six queries and the hit and miss behaviour need Desktop and the lab VM.
- The `.pbip` was hand written from the episode 1 project and has never been opened in Desktop. Whether Desktop accepts the `alternateOf` blocks, the Dual modes and `decimal(18,2)` as written is open.
- The M in the partitions is not parsed (no Power Query parser in this episode).
- `sys.dm_exec_query_stats` may keep a statement for a short time after the plan cache is cleared, and it only lists statements still in the cache. The demo notes what SQL Server shows.
- Part B (live connection to a published model, adding the local budget table, limited relationships) needs the tenant.
