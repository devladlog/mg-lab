# DEVLADLOG Power Apps #12 (Build Special) — Build a model-driven app from start to end

One Dataverse solution, **ContosoInspections** (publisher prefix `cin`), and the **Inspection Back Office** model-driven app
on top of it: app designer, site map, main and quick create forms, views, business rules, a business process flow, a
dashboard and charts, a command bar with Power Fx, security roles and column security, a custom page, and solution
packaging. The finished app is tested as the back-office user **Sam Demo**.

> **Schema note (read first).** When this episode was started the canvas special (episode 11) had no schema yet, so the
> ContosoInspections data model is **defined here**, in `src/schema/contosoinspections.schema.json`. Episode 11 has since
> written its own schema file and the two **do not match** (differences listed under "Reconcile with episode 11" below).
> One of them has to change before both episodes ship against the same tables.

## What is built

| Part | What it is | Where it lives | Built how |
|---|---|---|---|
| Data model | 4 tables, 3 relationships, autonumber `INS-{SEQNUM:5}`, alternate key on site code | `src/schema/*.json`, `src/solution/Entities` | generated, then **unpacked with pac** |
| Forms and views | main forms with tabs and subgrids, 2 quick create forms, 8 views (incl. quick find) | `src/solution/Entities/*/FormXml`, `SavedQueries` | generated |
| App and site map | `cin_InspectionBackOffice`, one area, three groups | `src/solution/AppModules`, `AppModuleSiteMaps` | generated |
| Dashboard and charts | 2 system charts, one 4-component dashboard | `src/solution/Dashboards`, `Visualizations` | generated |
| Security | roles *Inspection Back Office* and *Inspection Field Inspector*, field security profile, secured column `cin_reviewernotes` | `src/solution/Roles`, `Other/FieldSecurityProfiles.xml` | generated |
| Business rules | 5 rules, three scopes | `src/logic/business-rules.yaml` | **designer** (plan + executable check) |
| Business process flow | *Inspection review*, 4 stages | `src/logic/inspection-review.bpf.yaml` | **designer** (plan + check) |
| Command bar | approve, reject, flag for follow-up, review board (Power Fx) | `src/logic/commands.yaml` | **command designer**; formulas run in tests |
| Custom page | *Inspection review board*, named formulas, gallery, two buttons | `src/custom-page/Src/*.pa.yaml` | Power Apps source format v3.0; formulas run in tests |
| Seed data | 4 inspectors, 6 sites, 8 inspections, 13 items (fictional, `@contoso.com`) | `src/data/*.csv` | import |

Honest split: the **XML solution is generated by a script and was never imported into a tenant**. It packs and unpacks
cleanly with `pac` offline, but a successful pack is not a successful import (see gotchas). Business rules, the BPF and
the command bar are **not** in the solution XML: a business rule is a workflow row with XAML, a BPF is a process plus a
generated table, and modern commands live in a command component library. They are built in the designers (that is what
the recording shows) and the logic is checked locally from the plan files.

## Run and test (no tenant, no sign-in)

```bash
# 1. Python: schema, solution source, pac round trip, rules (needs pac on PATH; about 90 seconds, pac is slow)
cd tests/python && python3 -m pytest -q          # 75 passed

# 2. Power Fx on Microsoft's open-source interpreter (.NET 8 SDK; one build at a time)
cd tests/ContosoInspections.PowerFx.Tests && dotnet test -m:1     # 46 passed

# 3. Regenerate the solution source (deterministic GUIDs: running it twice changes nothing)
cd src/schema && python3 build_solution.py --profile full --out ../solution
python3 build_solution.py --profile data --out /tmp/cin-data-only   # starting point for the recording
```

Never run `pac auth` for any of this: pack and unpack are offline. Delete `bin`, `obj` and `__pycache__` afterwards (the
folder is about 1 MB without them).

### What the tests prove

- **Schema and source (pytest).** Every column, form control, view column, chart, role privilege and site map entry refers to
  something that exists; prefixes and option values are right; GUIDs are unique; the generated XML unpacks and **repacks to
  identical files**.
- **Rules (pytest).** The five business rules run against sample rows and behave as written, and every action is legal for its
  scope (for example Lock and Set Visibility are not allowed in a table-scope rule).
- **Commands (xunit).** Visible and OnSelect of all four commands run against in-memory tables built from the schema file with
  Dataverse-style names (`'Status (Inspections)'.Submitted`). Approve and reject confirm first, write, and report a refused
  write instead of claiming success. Flag for follow-up handles several selected rows.
- **Custom page (xunit).** Named formulas (`OpenCritical`, `PassRate`, `ScoreBand`, `Verdict`) and the gallery against the seed
  data with `Param("id")` set, including the zero-rows case; the two Navigate buttons' arguments; the pa.yaml files validate
  against the official v3.0 schema.

### What the tests cannot prove

The interpreter tests formula **logic**. They cannot test delegation, security, Dataverse plug-in behaviour, the command
designer's own limits, what the real `Navigate` does, or how forms render. Notify, Confirm, Navigate and `Self.Selected` are
stubs written for the harness (and `Self` is renamed `SelfHost` before evaluation because the Power Fx parser reserves `Self`).

## Gotchas we hit (each one has a test or a note)

- **App module and site map roots need `schemaName`, not an id.** In `solution.xml` the root components of type 80 (app
  module) and 62 (site map) written as `id="{guid}"` stop `pac solution pack` (2.16.1) with "RootComponent validation
  failed". They must be `schemaName="cin_InspectionBackOffice"`. Tables use `schemaName` too; dashboards, roles and field
  security profiles use `id`. A test turns the working file into the failing one to pin the message.
- **A missing dashboard is a warning, not an error.** A root component whose file is not in the folder packs with exit code 0
  and the warning "root components are not defined in customizations". Check the output text, not just the exit code.
- **Pack success is not import success.** `pac` never checks the XML against Dataverse. The only real proof is importing
  the zip, which this episode does **not** do (no tenant). See "Not verified".
- **`NotificationType.Success` is not supported in commands.** Learn: it shows an informational notification. The commands
  use the default `Notify(message)` for success and `NotificationType.Error` or `Warning` otherwise.
- **`Self.Selected.Item` is blank when more than one row is selected.** Learn: Item is blank if `SelectionMax <> 1`, so a
  single-record command cannot silently act on the first row. The bulk command uses `Self.Selected.AllItems`.
- **The form is saved before a command runs.** Learn (AutoSave): the form buffer is saved first, so unsaved edits are
  committed and problems appear in the form UI. Our reject command reads Reviewer notes right after that save.
- **`IsBlank("   ")` is false.** Reject used `IsBlank(notes)` first and a reviewer could reject with spaces; it now uses
  `IsBlank(Trim(notes))`, with a test.
- **A table-scope business rule also applies to canvas apps and the server.** Learn: scope Table = forms and server. Lock,
  Set Visibility, Set Business Required and Recommendation are form-scope only and are ignored server side. "A submitted
  inspection needs a score" is table scope on purpose so the canvas app (episode 11) gets the same error.
- **Business rules do not work with multi-select choices, file and language columns.** None of ours are multi-select.
- **Autonumber starts at the seed, 1000 by default.** `INS-{SEQNUM:5}` gives `INS-01000` first. Learn: the seed is **not
  included in a solution** when imported elsewhere, so after importing into test or production call `SetAutoNumberSeed` if
  the start value matters. Also, cancelled rows leave gaps.
- **Column security does not apply to system administrators.** By default only the system administrator role can read or
  set a secured column, and admins always can. Test *Reviewer notes* as **Sam Demo** (not as labadmin), with and without
  the *Inspection reviewer notes* field security profile.
- **Custom pages follow the model-driven app licence and do not count as apps.** `Navigate` from a page always opens inline
  (no dialog), cannot open a dashboard or a specific form, and only does anything when the page runs inside the app, not
  in Studio preview. Learn: after changing `OnStart` you must run it once from the App context menu.
- **BPF limits.** Learn: up to 30 stages per flow. A required step bound to a Yes/No column must be **Yes** to let the user
  move on, which is different from business-required fields on forms.
- **Dashboards hold up to six components; charts read at most 50,000 rows.** We use four components.
- **A plain-scalar `: ` breaks pa.yaml.** `Text: ="Suggested decision: " & Verdict` is invalid YAML; the formula is
  single-quoted in `ReviewBoard.pa.yaml`.
- **Local choices are named `'Column (Table plural)'`.** For example `'Status (Inspections)'.Submitted`; our first draft
  used the logical name and failed to bind.

## Reconcile with episode 11 (the canvas special)

Episode 11 wrote `src/schema/contosoinspections.schema.json` in its folder while this episode was being built. The data
models differ, so they are **not** one shared schema yet:

| | This episode (12) | Episode 11 |
|---|---|---|
| Tables | Inspector, Site, Inspection, **Inspection item** | Site, Inspector, Inspection, **Finding** |
| Inspection status | Draft, In progress, Submitted, Approved, Rejected | Draft, Submitted, Reviewed, Closed |
| Extra Inspection columns | Score (0-100), Requires follow-up, Follow-up date, Reviewer notes (secured), autonumber name | Result (Pass / Needs follow-up / Fail), Summary |
| Child table columns | Category, Severity (Info/Minor/Major/Critical), Passed, Notes, Resolved on | Severity (Observation/Minor/Major/Critical), Category, Details, Photo (image), Resolved, Resolve by |
| Site / Inspector | `cin_risklevel`, last inspected on, alternate key; phone, certified | Risk rating; Region, Work email, Certified |
| Schema format | `logicalName`, `[label, value]` options, `ui` and `security` sections | `schemaName`, label-only options, `securityRole`, `sampleData` |

Decision needed from the series owner: pick one model. The cheapest path is to adopt this episode's schema in episode 11
(it already covers the back-office needs: score, follow-up and reviewer notes), or to rename the child table and statuses
here. Do not ship both episodes against `ContosoInspections` until this is settled, because importing one solution over the
other would fail or merge columns.

## Not verified / needs the tenant

- **The generated solution XML has never been imported** into Dataverse. `pac solution pack` and `unpack` accept it; the
  import step may still reject something (form XML, saved query fetch XML, the app module, the sitemap, role privilege ids).
  `demo.md` has a fallback: build the tables by hand and compare against the generated solution afterwards.
- Business rules, the BPF, command bar formulas and the custom page were **never opened in the designers**. Their behaviour
  in the real command designer (for example which functions it rejects, how `Confirm` renders, whether the page opens with
  `Param("id")`) is from Learn plus local interpreter tests only.
- Column security, role access levels and the Sam Demo test need real users and a real environment.
- Power Apps premium licensing for Sam Demo (self-service trial in the lab) and the Copilot Studio trial were not touched.
- Learn limits quoted here were read in the docs, not exercised.
