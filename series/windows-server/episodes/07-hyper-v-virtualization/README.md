# DEVLADLOG Windows Server #7 — Hyper-V virtualization: audit the host, build a VM from a file, tame checkpoints

The five lab servers are Hyper-V VMs on the recording laptop, so this episode points the series at the layer under
them. One module, **HvLab**, driven by [`src/hv-lab.json`](src/hv-lab.json):

1. **Host audit.** A read-only collector runs on the Hyper-V host (host paths and volumes, every VM's generation,
   configuration version, memory, checkpoints, full disk chain, integration services, Secure Boot / TPM / nested
   settings, replication, switches). `Test-HvHost` turns the facts into findings: default paths on the system drive,
   disk and memory overcommit, vCPU ratio, generation 1, Secure Boot off, 50-checkpoint limit, too many / too old
   checkpoints, Standard checkpoints on a domain controller, Production checkpoints without VSS, automatic
   checkpoints, deep or broken disk chains, old configuration versions, nested virtualization needing version 8.0
   (and the Dynamic Memory / networking notes as Info), a heartbeat that is not OK, disabled integration services,
   unhealthy replication, and one Info line when several VMs share a parent disk.
2. **A VM from a file.** `Get-HvVmPlan` validates the `TestVm` spec and returns the ordered steps (`New-VHD`, `New-VM`,
   `Set-VM`, `Set-VMFirmware`, `Set-VMKeyProtector`, `Enable-VMTPM`, optional nested step). `New-HvLabVm` runs them
   with `-WhatIf` support and never touches an existing VM or disk.
3. **Checkpoint hygiene.** `Get-HvCheckpointPlan` (pure) decides what to keep: the newest N and anything named `KEEP-*`.
   `Invoke-HvCheckpointCleanup` removes the rest one at a time, then `Wait-HvDiskMerge` polls the live disk chain until
   Hyper-V has merged the `.avhdx` files.
4. **Tear-down.** `Remove-HvLabVm` only accepts allow-listed names and only deletes files under allowed roots, including
   the whole disk chain.

## Design choices

- **The host is the laptop, not a server.** The lab's VMs live on the recording laptop, so that is the host we audit.
  The collector uses only Hyper-V module cmdlets (not run on a real host yet, see the note below).
- **Facts on the host, rules anywhere.** Same pattern as the earlier episodes: only the collector script block travels
  (a test checks it calls no HvLab function and no state-changing cmdlet), facts are JSON, rules are pure.
- **Our policy in the JSON, Microsoft's limits in the code.** Thresholds such as "checkpoints older than 7 days" are
  policy and live in `hv-lab.json`. The 50-checkpoint maximum, the feature minimum versions and the integration
  service list come from Learn and are constants in the module.
- **Plan, then execute.** The VM spec and the checkpoint cleanup are pure plans first; the executing functions take
  `-WhatIf` and `Remove-HvLabVm` is guarded by an allow-list.
- **An empty VM on purpose.** `CON-HVT01` has no operating system. It exercises creation, firmware, vTPM, checkpoints
  and the disk chain without an installer, an evaluation licence or the shared VMs.
- **Rules with a reason.** Anything the audit says "(Learn)" about is documented; the rest is labelled as our policy.

## What we learned / gotchas

- **Production checkpoints can fall back to Standard.** With `-CheckpointType Production` Hyper-V creates a Standard
  checkpoint when a Production one fails; `ProductionOnly` creates none. Production checkpoints use VSS in the
  guest, so a VM with the VSS integration service disabled (or no OS) is a candidate for the fallback. The audit
  flags the combination; what an OS-less VM does on the recording day is recorded in demo.md, not assumed.
- **Standard checkpoints and Active Directory.** Learn warns that a Standard checkpoint can cause data consistency
  problems with systems that replicate between nodes such as Active Directory. The audit is High for a Standard
  checkpoint on anything listed in `Policy.DomainControllers`.
- **The limit is 50, "dependent on the amount of available storage".** That is Learn's maximum for Windows Server
  2016 to 2025. Our policy (`MaxCheckpoints: 3`) is far lower on purpose: every checkpoint is one more differencing
  disk.
- **Deleting a checkpoint does not finish the job.** `Remove-VMCheckpoint` returns while Hyper-V merges the `.avhdx`
  into its parent in the background. `Wait-HvDiskMerge` watches the real chain and warns instead of deleting files
  when the timeout is reached.
- **Configuration version is one-way, and gates features.** Learn's table: Production checkpoints 6.2, vTPM 7.0,
  nested virtualization 8.0 (Intel; 9.3 for AMD), hibernation 9.0, GPU partitioning 12.0. Upgrading the version
  can't be undone, so the audit reports and never upgrades.
- **Nested virtualization.** Needs version 8.0 or higher on Intel (Learn), the VM off while you run
  `Set-VMProcessor -ExposeVirtualizationExtensions $true`, and for nested guests MAC address spoofing or a NAT
  switch. Dynamic Memory is reported as Info, not as an error: Learn says enabling nested virtualization alone has
  no effect on it, but once Hyper-V runs inside the VM, memory no longer fluctuates.
- **"Running" is not a heartbeat.** `State = Running` only means Hyper-V set resources aside (Learn); the Heartbeat
  integration service shows whether the guest answers.
- **Differencing disks share a parent.** Lab VMs are often children of one base image (the sample fixture is built
  that way; whether the real lab is, the recording shows). Moving or editing a shared parent breaks every child;
  the audit says so as an Info line.
- **We hit the PowerShell parser ourselves again.** `"$VmName: disk chain..."` is read as a drive-qualified variable
  and the module fails to load; `"${VmName}: ..."` fixes it (same rule as episode 6).
- **Pester can only mock what exists, and only what it can bind.** On Linux the Hyper-V cmdlets are stubs with the
  parameter names the module passes; switch parameters (`-TurnOff`, `-Force`) must be typed `[switch]` in the stub.
