# DEVLADLOG Windows Server #6 — Windows Admin Center: one gateway, shared connections, SSO and read-only access

Four of the five lab servers are Server Core. This episode puts **Windows Admin Center (Administration Mode)** on
**CON-SRV02** as the lab's gateway and automates everything around the installer with one module, **WacLab**, driven
by [`src/wac-lab.json`](src/wac-lab.json):

1. **Preflight.** A collector runs on the future gateway (domain role, OS build, domain membership, listeners on the
   HTTPS port, the TLS certificate if one is configured, and every node over WinRM/CIM). `Test-WacGateway` turns the
   facts into findings: gateway on a domain controller (unsupported), not domain-joined, port taken, certificate
   missing / expired / expiring / no Server Authentication EKU / wrong name, self-signed (60 days, testing only),
   Virtualization Mode minimums (4 cores, 8 GB, 10 GB), more nodes than Administration Mode is sized for, unreachable
   or old nodes, SSO configured for a DC.
2. **Silent install** with the switches documented on Learn: `/VERYSILENT /Mode=Administration`, plus
   `/HTTPSPortNumber` and `/CertificateThumbprint` only when set; then wait for the `WindowsAdminCenter` service.
3. **Shared connections as a file.** `ConvertTo-WacConnectionCsv` writes `"name","type","tags","groupId"` with FQDNs,
   the documented type strings, pipe-separated tags and `global` (shared). `Test-WacConnectionCsv` checks any CSV
   strictly (header case, quoting, type, FQDN, groupId) before `Import-WACConnection` runs.
4. **Single sign-on** with resource-based Kerberos constrained delegation from the gateway to each node with
   `KerberosSso: true`. `Set-ADComputer -PrincipalsAllowedToDelegateToAccount` *replaces* the list, so
   `Get-WacDelegationPlan` always writes current principals + the gateway (and `-Remove` takes only the gateway out).
   Domain controllers are skipped unless `-IncludeDomainControllers`.
5. **RBAC check.** After *Apply role-based access control* in the UI (a JEA endpoint `Microsoft.Sme.PowerShell` and
   three local groups on the node), `Add-WacRbacMember` puts the configured members in the role groups and
   `Test-WacRbac` reports missing or unexpected members. `CONTOSO\alex.demo` is a **Reader** on CON-SRV01.

## Run it in the lab

On **CON-SRV02**, elevated **Windows PowerShell 5.1**, as a lab domain admin, in `src`:

```powershell
.\Invoke-WacPreflight.ps1 -FactsFile .\gateway-facts.json -OutFile .\preflight.md -FailOnHigh
.\Deploy-WacLab.ps1 -Step Install -InstallerPath C:\lab\WindowsAdminCenter.exe
.\Deploy-WacLab.ps1 -Step Connections -AccessKey (Read-Host -AsSecureString 'Access key') -Credential (Get-Credential)
.\Deploy-WacLab.ps1 -Step Sso -WhatIf; .\Deploy-WacLab.ps1 -Step Sso        # needs RSAT-AD-PowerShell
# In the UI: con-srv01 > Settings > Role-based access control > Apply, then:
.\Deploy-WacLab.ps1 -Step Rbac
```

See [demo.md](demo.md) for why the gateway is CON-SRV02 (and not the DC or the laptop), the five screens and tear-down.

## Design choices

- **CON-SRV02 is the gateway.** Not the DC (unsupported), not the recording laptop (not domain-joined: Windows 11 is
  only a local-client topology and group-based access doesn't work in a workgroup). A domain member gives AD-group
  gateway access, Kerberos to the nodes and the production shape: one shared gateway, every admin with a browser.
- **Facts on the gateway, rules anywhere.** Same pattern as episodes 1 to 4: only the collector script block travels
  (a test checks it calls no WacLab function), facts are saved as JSON, rules are pure and tested offline.
- **Only documented values.** Connection types are the two strings Learn's table lists; installer switches are the
  ones on the install page. Anything else is refused instead of guessed.
- **Delegation is read-modify-write.** The plan carries the full principal list; `-Remove` takes out only our
  gateway and clears the attribute with `$null` (as Learn shows) only when nothing else is left.
- **No delegation to domain controllers by default.** The DC is managed with *Manage as*; an admin who really wants
  SSO to a DC has to say `-IncludeDomainControllers`.
- **RBAC through the UI, membership through code.** Learn's single-machine path (Apply in the UI) installs the
  `Microsoft.Sme*` modules and the endpoint with DSC; we don't re-implement it. We automate the part that drifts: who
  is in each role group.
- **The access key is a `SecureString`** and is turned into text only for the `Import-WACConnection` call, through
  `PSCredential.GetNetworkCredential()` (the episode 4 lesson about `Marshal::PtrToStringAuto`).

## What we learned / gotchas

- **`Set-ADComputer -PrincipalsAllowedToDelegateToAccount` replaces the list.** The parameter *sets*
  `msDS-AllowedToActOnBehalfOfOtherIdentity`, and the cmdlet page warns that running it without the existing first
  principal overrides it. Learn's SSO one-liner is fine on a clean lab; with a second gateway it silently drops the
  first one. Tests cover add-and-keep, remove-only-ours and clear.
- **The example CSV on Learn has two errors.** Line 3 uses `msft.sme.connection-type.windows-server`, which isn't in
  the page's own type table, and line 5 is missing a closing quote after the name. The page also says the CSV is
  case-sensitive. `Test-WacConnectionCsv` finds both (a test runs it on a verbatim copy).
- **The module path on Learn doesn't parse.** `Import-Module "$env:'Program Files'\WindowsAdminCenter\PowerShellModules\..."`
  fails in PowerShell 7.6 with `InvalidVariableReferenceWithDrive` (a test parses it), and the extensions example on
  the same page uses another layout (`windows admin center\PowerShell\Modules\ExtensionTools`).
  `Find-WacPowerShellModule` searches both layouts under `$env:ProgramFiles` and says where it looked.
- **We hit the same parser rule ourselves:** a message string `"... don't include $fqdn: browsers will warn"` made the
  whole module fail to load, because `$fqdn:` reads as a drive-qualified variable. Fixed with `${fqdn}`.
- **Two modes, chosen at install.** Administration Mode (stateless, PowerShell remoting, described as up to about 10
  managed nodes) or Virtualization Mode (PostgreSQL, agents, up to 1,000 nodes, 4 cores / 8 GB / 10 GB minimum,
  dedicated server). Changing mode means reinstalling, and they can't share a machine.
- **Port and certificate defaults.** On Windows Server the gateway is configured for remote access on 443 (Windows
  client: 6600). Without a certificate the installer generates a self-signed one that expires after 60 days.
- **RBAC is JEA.** Applying RBAC installs `Microsoft.Sme*` modules, registers the JEA endpoint
  `Microsoft.Sme.PowerShell` (temporary local admin per user) and creates *Windows Admin Center Administrators /
  Hyper-V Administrators / Readers*. It restarts WinRM and can take up to 10 minutes. With limited access, the
  PowerShell, Remote Desktop and Storage Replica tools are unavailable and Files has no upload or download.
  RBAC isn't supported for cluster management.
- **Gateway access isn't server access.** Gateway users still need admin rights (or an RBAC role) on each node;
  local administrators of the gateway machine are always gateway administrators.
- **Only the latest version is supported**: Microsoft's FAQ asks you to upgrade within 30 days of a release, so the
  version on screen will differ from the one in this README.
- **Pester can only mock what exists**: `Get-ADComputer`, `Set-ADComputer`, `Get-Service`, `Start-Service`,
  `Invoke-Command` and `Import-WACConnection` are stubbed with the parameters the module passes.
