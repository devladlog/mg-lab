# DEVLADLOG Windows Server #5 — PowerShell Automation: no password, no admin rights, still automated

Episodes 1 to 4 ran everything as the lab Administrator. This one fixes the classic unattended job ("restart IIS at
3 AM, as a domain admin, password in the task") with three pieces that only use what ships with Windows Server:

1. **A JEA endpoint from a JSON file.** [`src/jea-definition.json`](src/jea-definition.json) describes the endpoint
   `Contoso.AppOps` for the app server CON-SRV01: role **AppOpsReader** (`Get-Service`, `Get-OpsHealth`) and role
   **AppOpsOperator** (`Restart-Service -Name` limited to `W3SVC`/`WAS`, `Clear-OpsLogFolder`), mapped to
   `CONTOSO\GG-AppOps-Readers` and `CONTOSO\GG-AppOps-Operators`, virtual account, transcripts.
   `Install-OpsEndpoint` builds the `ContosoOps` module with its `RoleCapabilities` folder (`New-PSRoleCapabilityFile`
   per role), writes and tests the session configuration (`New-PSSessionConfigurationFile`,
   `Test-PSSessionConfigurationFile`) and registers it. It refuses to register when the lint has a High finding.
2. **A lint for JEA definitions.** `Test-OpsEndpointDefinition` checks each role (wildcards, Learn's list of
   dangerous commands, unconstrained state-changing cmdlets, ValidateSet + ValidatePattern, unanchored patterns,
   relative external commands), each group **after merging its roles** with Learn's seven merge rules
   (`Merge-OpsRoleCapability`), the session (virtual account = local admin, Domain Admins on a DC; no transcripts;
   `localhost\` principals) and the functions module (visible functions that don't exist, `Invoke-Expression`,
   `Add-Type`, `[scriptblock]::Create`). Accepted risks stay in the report with their reason; High can't be accepted.
3. **A runbook that only talks to that endpoint**, run by Task Scheduler on CON-SRV02 as the gMSA
   `CONTOSO\gmsa-opsjob$` (member of the Operators group, nothing else). Each run: connect with implicit remoting
   (retry with exponential backoff), read health, decide (`Get-OpsDecision`, pure), act (no retry), re-check, log one
   JSON line per event, exit 0 or 1. A circuit breaker reads its own logs: after 3 restarts of a service in 24 h it
   stops restarting and raises a High alert.

## Design choices

- **Commands, not admin rights.** Restarting W3SVC needs admin rights; the operator gets them only inside the endpoint,
  through a temporary virtual account, for two services. The virtual account being a local administrator is a known,
  accepted risk, written in the definition with its reason (the lint shows it as `Accepted`).
- **Lint the merge, not just the roles.** A user gets the most permissive union of all their roles. Each role can look
  fine on its own and the group still ends up with an unconstrained `Restart-Service` (the `risky-definition.json`
  case). `Merge-OpsRoleCapability` implements Learn's merge rules and its own example is a test.
- **Functions do the provider work.** JEA sessions have no providers. `Clear-OpsLogFolder` deletes files on the user's
  behalf, but the user only picks an age (7 to 365 days); the folder and the `*.log` filter are fixed in the module.
  The lint fails if the module uses `Invoke-Expression`, `Add-Type` or `[scriptblock]::Create`, because function bodies
  aren't constrained by JEA.
- **Decide, then act.** `Get-OpsDecision` is pure (health + policy + history in, actions + alerts out), so every rule
  is tested without a server, and `-HealthFile` replays a saved state.
- **Retry reads, never writes.** Connections and health reads use `Invoke-OpsWithRetry` (5, 10, 20 s, capped at 60).
  A failed restart is logged as `Failed` and the run exits 1; it's not retried blindly. After a restart the job reads
  health again and raises `RestartDidNotHold` if the service isn't running.
- **The job never reboots** and has no command to do it. A pending reboot is an alert for a maintenance window.
- **The gMSA writes only its logs.** Code in `C:\OpsJob` is writable by administrators only; the gMSA gets Modify on
  `C:\OpsJob\logs`. JEA transcripts on CON-SRV01 are written by Local System, outside the job's reach.

## What we learned / gotchas

- **JEA sessions are NoLanguage.** Learn: you can't use variables or inspect object properties in a JEA session. A
  runbook can't `Invoke-Command -ConfigurationName ... { $svc = 'W3SVC'; Restart-Service $svc }`. We use implicit
  remoting (`Import-PSSession -CommandName ... -Prefix Jea`), which Learn recommends for automating against JEA: the
  proxies run locally in full language. We import only the three commands we need, by name, because Learn notes that
  importing a whole JEA session can fail on the default cmdlets.
- **Role merging widens access.** Learn's rules: if one role exposes a cmdlet without parameter constraints, all
  parameters are allowed; if one role allows a parameter without a ValidateSet, other roles' sets for that parameter
  are ignored; a ValidatePattern anywhere makes the ValidateSets for that parameter ignored. The lint reports each
  dropped constraint per group (`MergeWidening`).
- **ValidatePattern beats ValidateSet on the same parameter** (Learn), so a definition with both is a Medium finding.
- **Virtual accounts are administrators by default**: local Administrators on a member server, **Domain Admins on a
  domain controller** (Learn). With `RunAsVirtualAccountGroups` they get only the listed local groups. The lint raises
  `VirtualAccountIsAdmin` to High when `TargetRole` is `DomainController`.
- **Registering or unregistering an endpoint restarts WinRM** and ends every remoting session (Learn). Install over
  PowerShell Direct or at the console, never over the WinRM session you're using.
- **To change roles-to-groups you re-register** (unregister + register); role capability (.psrc) edits apply to new
  sessions without re-registering, which is why only trusted admins may write to the module folder (Learn).
- **Role capability names must be unique.** JEA picks the first `.psrc` with the name it finds in `PSModulePath`, in
  no guaranteed order (Learn). Ours live in one module.
- **KDS root key for a lab.** gMSAs need a KDS root key; normally domain controllers wait up to 10 hours after creating
  it. `Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))` skips the wait and Learn documents it only for test
  environments with one DC. Deleting and re-creating root keys can leave the old one cached, so tear-down keeps it.
- **gMSA names are unique per forest**, not per domain, and the password interval can only be set at creation (Learn).
- **Pester 6 has no fall-through for filtered mocks.** Mocking `New-Item` only for `C:\...` paths made every other
  `New-Item` call fail with "No mock ... matched". The test adds a default mock that calls
  `Microsoft.PowerShell.Management\New-Item @PesterBoundParameters`.
- **PowerShell 7 turns ISO dates in JSON into `DateTime`.** Our log writes `"TimestampUtc":"2026-11-20T09:00:00Z"`, but
  `ConvertFrom-Json` hands back a `DateTime`, so the test compares the raw line. The restart history handles both: a
  `DateTime` is used as is (7), a string is parsed with `InvariantCulture` (5.1). Re-parsing the `DateTime` as text
  would depend on the server's culture.
- **Pester can only mock commands that exist**, so the JEA, CIM and service cmdlets are stubbed with every parameter
  the code passes (same lesson as episodes 2 to 4).
