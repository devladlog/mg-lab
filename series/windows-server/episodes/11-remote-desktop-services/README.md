# DEVLADLOG Windows Server #11 — Remote Desktop Services: check the deployment, read the plan, then change it

Episodes 1 to 10 built and hardened the lab; this one lets people sign in to it. One module, **RdsLab**, driven by
[`src/rds-lab.json`](src/rds-lab.json), for a small session-based Remote Desktop deployment (one Desktop Experience server
with the Connection Broker, Session Host, Web Access and Licensing role services):

1. **Check.** A read-only collector runs on the connection broker (servers and role services, license configuration,
   certificates, the session collection's connection and security settings, user sessions) and on each session host
   (installation type, licensing grace period, license server list). `Test-RdsDeployment` turns the facts into
   findings (High / Medium / Low / Info): no deployment, missing role services, a session host on Server Core, a
   grace period that is ending or over, licensing mode, self-signed or expiring certificates, an open user group,
   NLA, security layer, encryption level, missing idle and disconnected-session limits.
2. **A plan before any change.** `Get-RdsDeploymentPlan` builds only the steps that differ from the policy (install role
   services, add licensing, license mode, create the collection, collection settings) and remembers the value it found
   (`Before`). The role install is marked **Disruptive**; the certificate step is **Manual** (the script never picks a
   certificate).
3. **Apply with -WhatIf.** `Invoke-RdsDeploymentPlan` runs one step at a time, only five allow-listed RemoteDesktop
   cmdlets, and the disruptive step only with `-AllowDeployment`. The plan is recomputed from the facts, so re-running
   after a restart is safe.
4. **Sessions.** `Get-RdsSessionSummary` counts active and disconnected sessions per host;
   `Invoke-RdsDisconnectedLogoff` logs off *disconnected* sessions of a named user (mandatory `-UserName`, `-WhatIf`).

## Design choices

- **Same shape as episodes 1 to 10.** A collector that only reads, pure rules, a report. The collectors have a test
  that fails if they ever call a `Set-/New-/Remove-/Add-/Invoke-/Disconnect-/Send-RD*` cmdlet.
- **Two collectors, one hop each.** The broker collector runs on the broker (the RemoteDesktop cmdlets live there); the
  host collector runs on each session host, started from the machine you run the check on. Starting the host check from
  inside the broker session would be a second WinRM hop, and credentials are not delegated by default.
- **Our policy in the JSON, Microsoft's values in the code.** "30 idle minutes", "per user", "SSL" are our policy. The
  licensing modes (`PerDevice`, `PerUser`, `NotConfigured`), the security layers (`RDP`, `Negotiate`, `SSL`), the
  encryption levels (`None`, `Low`, `ClientCompatible`, `High`, `FipsCompliant`), the role-service names and the
  certificate roles and levels come from Learn and are checked on load.
- **FQDNs.** The deployment cmdlets take fully qualified names (Learn: `New-RDSessionDeployment`, `Add-RDServer`), so the
  config rejects a short name.
- **Only differences become steps, and each remembers what it found.** Like episode 8's rollback file, but for a plan
  you can re-run: the plan is rebuilt from fresh facts every time, so a restart halfway does not need bookkeeping.
- **Disruptive and manual are different things.** Installing role services is automated behind `-AllowDeployment`;
  choosing a certificate is never automated.
- **An allow-list for what a plan may run.** `Invoke-RdsDeploymentPlan` refuses any step whose cmdlet is not one of the
  five RemoteDesktop cmdlets, so a plan read from a file cannot run something else.
- **Logoff is narrow on purpose.** `-UserName` is mandatory, only disconnected sessions are touched, and
  `Invoke-RDUserLogoff` closes the user's applications (Learn).

## What we learned / gotchas

- **The RD Session Host is not in Server Core.** Learn's "Roles not in Server Core" says some Remote Desktop role
  services are included (Connection Broker, Licensing, Virtualization Host) but Gateway, **RD Session Host** and **Web
  Access** are not. Four of the five shared lab VMs are Server Core, so this episode needs an extra Desktop Experience
  VM. The check flags a Core session host as High (`SessionHostOnServerCore`).
- **There is a licensing grace period of 120 days** during which no license server is needed; after it, clients need an
  RDS CAL issued by a license server (Learn). It is readable with `Win32_TerminalServiceSetting.GetGracePeriodDays()`
  (0 means over). A Microsoft Q&A answer (community, not documentation) says the counter keeps showing after CALs are
  activated until the server actually issues licenses; we did not verify that, so the check only talks about the grace period
  while *no license server* is configured.
- **Per user CALs are not enforced.** The server issues a CAL from the pool or the over-used pool, and counting is the
  administrator's job (Learn); per device CALs cannot be over-allocated and a temporary one lasts 90 days. The check
  reports the mode and never claims compliance.
- **CAL and license server versions matter.** RDS CALs for an older Windows Server version cannot be used on a Windows
  Server 2025 session host, and a Windows Server 2025 license server can hold CALs of 2016 to 2025 (Learn tables).
- **The "licensing mode is not configured" balloon is not always a problem.** Learn lists a local account with per user
  mode and an administrative session as cases where it appears even when everything is right.
- **Certificate levels.** `Get-RDCertificate` returns `Not Configured`, `Untrusted` (self-signed) or `Trusted`
  (enterprise or public) per role (RDGateway, RDWebAccess, RDRedirector, RDPublishing); the check uses exactly that.
- **PowerShell under StrictMode.** `(Get-WithRole $x).Count` fails when a function returns one object (the property does
  not exist on a single custom object); count inside the function instead. We hit this in the first test run.
- **Pester and modules.** Mocking a cmdlet that the *module* calls needs `-ModuleName RdsLab` on both `Mock` and
  `Should -Invoke`; `-ModuleName $null` mocks nothing. The global stub functions also need
  `SupportsShouldProcess` and the parameters we splat, or binding fails.

> **Not run yet (needs the lab, see [demo.md](demo.md)):** both collectors on a real server. Learn documents the cmdlet
> parameters but **not the property names of the objects** that `Get-RDServer`, `Get-RDLicenseConfiguration`,
> `Get-RDSessionCollectionConfiguration` (`-Connection`, `-Security`, `-UserGroup`) and `Get-RDUserSession` return. The
> collector assumes they mirror the `Set-RDSessionCollectionConfiguration` parameter names (`IdleSessionLimitMin`,
> `AuthenticateUsingNLA`, ...), `Roles`/`Server`, `Mode`/`LicenseServer`, `SessionState`, `UnifiedSessionId`, and records
> a CollectorError for anything else; the fixtures use that assumed shape. Also unverified: that `0` means "no limit"
> for the three session limits, the exact `SessionState` text (matched loosely on `ACTIVE` / `DISCONNECT`), what
> `Get-RDServer` does on a server with no deployment yet, whether the server restarts during
> `New-RDSessionDeployment`, `Get-WmiObject ... -Authentication PacketPrivacy` returning the grace period under
> Windows PowerShell 5.1 remoting, and every apply step. Only parsed and unit-tested here.
