# DEVLADLOG .NET #3 — Entity Framework Core 10: migrations, concurrency, SQLite locally, Azure SQL in Azure

Episode 1's project requests API kept everything in memory, so a restart (or an App Service setting change) wiped
the data. This episode moves it to **Entity Framework Core 10** on **.NET 10 (LTS)**:

- **One model, two providers**: SQLite for local development and tests, **Azure SQL Database** (free offer) in Azure.
  Each provider keeps **its own set of migrations** (`Migrations/Sqlite`, `Migrations/SqlServer`) using the
  "one context type per provider" approach from Learn: `SqliteRequestsDbContext : RequestsDbContext`.
- **Fluent configuration** in `IEntityTypeConfiguration<T>` classes: max lengths, `decimal(18,2)`, enums stored as
  strings, a restricted foreign key, a unique index, **reference data with `HasData`** ("model managed data"), and a second migration that adds
  an index (`AddStatusPriorityIndex`).
- **Projections, not entities**: every read uses one `Expression<Func<ProjectRequest, RequestDto>>`, which EF Core
  translates to a single `SELECT` with a `JOIN` and tracks nothing. The summary endpoint's `COUNT`/`SUM` run in the
  database.
- **Optimistic concurrency across HTTP requests**: an application-managed `Guid Version` concurrency token (works on
  SQLite *and* SQL Server). Writes send the version the client read; EF Core puts it in the `UPDATE ... WHERE`, and a
  `DbUpdateConcurrencyException` becomes **409**. "Approve what you saw, or nothing."
- **Deployment without passwords**: App Service's managed identity connects with
  `Authentication=Active Directory Default`; the schema is applied from a **reviewed, idempotent SQL script**, and the
  app's database user only gets `db_datareader` + `db_datawriter`.

## Build, test, run

```bash
dotnet tool restore                      # dotnet-ef 10.0.15 from the local manifest
dotnet test -m:1                         # Passed: 26, Failed: 0 (10 data + 12 API + 4 configuration), ~4 s

cd src/ProjectRequests.Api
dotnet dotnet-ef database update --context SqliteRequestsDbContext   # creates requests.db, 2 migrations, 3 departments
dotnet run --launch-profile http         # http://localhost:5207, SQL logged to the console (Development)
cd ../.. && ./deploy/local-demo.sh       # 201, 200, 200, 409, 200, 200, summary
```

Tested with .NET SDK 10.0.115 / runtime 10.0.15, EF Core 10.0.15 (SQLite + SQL Server providers) on Linux.
No SQL Server or Docker was available here: everything that runs, runs on SQLite; the SQL Server side is verified
**without a server** (model has no pending changes, `decimal(18,2)` mapping, retrying execution strategy, and the
committed idempotent script equals what `IMigrator` generates). Applying it to Azure SQL is a lab step (demo.md).

### Changing the model

```bash
cd src/ProjectRequests.Api
dotnet dotnet-ef migrations add <Name> --context SqliteRequestsDbContext    # goes next to the SQLite migrations
dotnet dotnet-ef migrations add <Name> --context RequestsDbContext          # SQL Server, via SqlServerDesignTimeFactory
dotnet dotnet-ef migrations script --idempotent --context RequestsDbContext --output ../../deploy/sqlserver-migrations.sql
```

The first time, add `--output-dir Migrations/Sqlite` / `Migrations/SqlServer`; later migrations go next to the last one.

```bash
./deploy/local-demo.sh https://<app-host>
az group delete --name rg-mglab-net03 --yes                               # tear down
```

Azure SQL Database **free offer**: 100,000 vCore seconds, 32 GB data and 32 GB backup storage per database per
month, up to 10 free databases per subscription; with `AutoPause` it pauses at the limit instead of billing. App
Service plan **Free F1, Linux**. The Azure/Entra steps were **not run in this container**.

## What we learned / gotchas

- **Dates came back without the `Z`.** Right after `POST` the API returned `"createdAtUtc": "...Z"`; the same value
  read back with `GET` had no `Z`. Databases don't store `DateTime.Kind`, so EF Core materialises `Unspecified`, and
  System.Text.Json then omits the offset. Learn documents this for SQL Server; we saw it on SQLite. Fix: one
  pre-convention rule, `configurationBuilder.Properties<DateTime>().HaveConversion<UtcDateTimeConverter>()`, which
  also covers `DateTime?`. Three API tests pin it.
- **`DateTimeOffset` is the wrong type for SQLite.** Episode 1 used `DateTimeOffset CreatedAt`. Learn: SQLite can
  store it and compare for equality, but ordering and comparisons aren't translated to SQL. We switched to
  `DateTime CreatedAtUtc` (Learn's recommendation) — which is what led to the gotcha above.
- **SQLite compares strings case-sensitively, SQL Server (default collation) doesn't.** `?department=fin` found
  nothing on SQLite. Rather than writing provider-specific SQL, the API normalises codes to upper case; a data test
  documents the SQLite behaviour so nobody "simplifies" the normalisation away.
- **Migrations are provider-specific.** `dotnet ef` only scaffolds for the active provider, and SQLite can't
  generate idempotent scripts. Hence two context types and two migration folders. The SQL Server set is generated
  through an `IDesignTimeDbContextFactory` with a dummy connection string — adding migrations and scripting them
  never connects.
- **`HasPendingModelChanges()` catches the forgotten migration** for both providers, without a database server
  (EF Core 9+ also makes `Migrate()` throw in that situation). We also compare the committed `.sql` with
  `IMigrator.GenerateScript(..., Idempotent)`, so the script the DBA reviews is never stale.
- **Concurrency token = the version the *client* saw.** Loading the row and saving it only protects the few
  milliseconds between our `SELECT` and `UPDATE`. Setting `Entry(e).Property(r => r.Version).OriginalValue` to the
  version from the request body (the pattern from Learn's Razor Pages concurrency tutorial) protects the minutes the
  approver spent looking at the screen. Removing that one line makes the 409 test fail (we tried).
- **SQLite has no `rowversion`**, so we use an application-managed `Guid` token and must call `Touch()` on every
  write. The `UPDATE` only sets the columns that changed, plus `Version`, and adds `AND "Version" = @p` (see
  `deploy/local-demo.sql-log.txt`).
- **Integration tests on SQLite need a file (or an open connection).** An in-memory SQLite database is deleted when
  its connection closes, and EF Core opens/closes connections per command. Data tests keep one connection open; API
  tests use a temp file per test class instance and call `SqliteConnection.ClearAllPools()` before deleting it.
- **`UseSetting` in `WebApplicationFactory` is visible to code that reads configuration before `Build()`** (our
  provider switch) on .NET 10 — we checked: the tests never touched the `requests.db` in the project folder.
- **The publish package grew from 368 KB (episode 1) to 43 MB.** SQLite and SqlClient (MSAL) bring native libraries
  for every OS; `libmsalruntime.so` alone is 37 MB. Publishing with `--runtime linux-x64 --self-contained false`
  brings the zip to 18 MB.
- **Development logs every SQL command** (`Microsoft.EntityFrameworkCore.Database.Command: Information`), parameter
  values show as `?` (sensitive data logging is off). `appsettings.json` sets that category to `Warning` so
  production doesn't log every query.
- **`HasData`, not `UseSeeding`, for the departments.** Learn now recommends `UseSeeding`/`UseAsyncSeeding` for
  general seeding, but its own table says SQL scripts don't run seeding delegates. `HasData` rows become
  `InsertData` operations inside the migration, so they're in `sqlserver-migrations.sql` too. The price: fixed
  primary keys, and changing the data needs a new migration.
- **Runtime migrations are opt-in.** `Database:MigrateOnStartup` is only `true` in tests. Learn prefers a reviewed SQL
  script or a migration bundle for production, and a deployment identity with schema rights separate from the app's
  identity — so the app's database user has no `db_ddladmin`, unlike the Learn quickstarts.
- **Free-offer databases auto-pause after 15 minutes idle**, so the first request after a pause is slow;
  `EnableRetryOnFailure()` on the SQL Server provider retries transient errors. And managed identity tokens are cached:
  grant the database roles *before* the app's first request (Learn's tutorial note).
